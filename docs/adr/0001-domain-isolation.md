# ADR-0001: 领域隔离架构

| 项目 | 内容 |
|------|------|
| 状态 | 已接受 |
| 日期 | 2026-09-22 |
| 决策者 | 项目负责人 |

## 背景（Context）

本项目需要同时服务两个差异极大的学习领域：

1. **初中语文**：面向孩子，题型包括古诗词背诵、文言文翻译、阅读理解、作文等，需要严格对齐教材和考试标准
2. **人文社科**：面向成人自用，内容包括历史、哲学、社会学、经济学等，题型灵活，以开放题和论述题为主

如果把两个领域的代码混在一起，会出现以下问题：
- 语文的"标准答案思维"会限制人文社科的开放性
- 人文社科的灵活题型会污染语文的严谨评分逻辑
- 任何一个领域的改动都可能影响另一个领域
- 未来如果要新增第三个领域（如英语），没有清晰的接入模式

## 决策（Decision）

采用**共享内核 + 领域插件**的架构：

1. **共享内核（Kernel）**：只包含与领域无关的通用能力
   - FSRS-6 间隔重复调度算法
   - 统一数据模型（Item / AnswerRecord / KnowledgePoint / GradeResult）
   - 进度统计与学习曲线渲染
   - 知识图谱基础渲染引擎

2. **领域插件（Domain Plugin）**：每个领域独立实现四个标准接口
   - `TemplateProvider`（题目模板）
   - `AnswerCollector`（作答器）
   - `Grader`（批改器）
   - `GraphBuilder`（图谱构建器）

3. **接口契约（Contract）**：四个接口的输入输出严格定义在 `docs/contracts/` 中，任何领域插件必须遵守

4. **防浆糊机制**：
   - 所有架构决策记录在 `docs/adr/` 中
   - 接口变更必须更新契约文档并记录 ADR
   - 领域代码不得直接引用另一个领域的内部实现

## 后果（Consequences）

### 正面
- 两个领域完全隔离，互不影响
- 新增领域只需实现四个接口，内核零改动
- 接口契约清晰，降低沟通成本
- 内核代码可复用、可测试

### 负面
- 初期需要额外的抽象设计成本
- 四个接口的设计需要足够通用，否则后期可能需要调整
- 领域开发者需要理解契约文档

### 风险
- 如果某个领域的需求超出四个接口的能力范围，需要扩展接口，此时必须同步更新所有已实现的领域插件
- 缓解措施：接口设计预留扩展点（如 `meta` 字段），重大变更走 ADR 流程

## 备选方案（Alternatives Considered）

1. **完全分离两个项目**：语文一个仓库，人文社科一个仓库
   - 否决原因：FSRS 调度、数据模型、图谱渲染需要写两遍，维护成本翻倍

2. **单项目但按目录分模块**：不做接口抽象，只是代码放在不同目录
   - 否决原因：没有强制隔离，时间长了必然出现跨领域引用，最终变成"浆糊代码"

3. **微服务架构**：每个领域一个独立服务
   - 否决原因：个人自用项目，过度设计，运维成本过高
